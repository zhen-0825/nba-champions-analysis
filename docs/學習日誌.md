### 【今天新增的比較】

- **問題**：冠軍隊是靠「一組固定的核心五人」打出優勢，還是靠很多組陣容輪流上場？
- **假設**：冠軍會有一組核心五人，同時在場的時間明顯比其他組合多、淨效率比全隊平均高；奪冠那季，這組用得比該隊其他球季更多。
- **圖表**（頁面：冠軍故事 → 上場陣容）：
  1. **陣容地圖**（散點圖）：每個圈是一組 5 人陣容，橫軸＝同時在場分鐘、縱軸＝淨效率，虛線＝全隊整季淨效率。在場最久的 3 組標上「第 1～3 組」。
  2. **在場最久的 10 組**（表格）：分鐘長條、佔全隊時間、戰績、進攻／防守／淨效率。
  3. **每一位冠軍的核心五人**（啞鈴圖）：灰點＝全隊整季淨效率、彩色點＝核心五人的淨效率，線越長差距越大；可點開看名單。
  4. **逐季**：長條＝核心五人佔全隊時間（紫色＝奪冠季），折線＝前 5 組合計佔比，看奪冠那季是不是更固定用同一組人。
- **讀法**：先看第 3 張，彩色點是不是大多在灰點右邊（核心比全隊好）；再看第 4 張，紫色長條是不是比灰色高（奪冠時更依賴核心）。兩個都「是」，假設就成立。

### 【今天的技術原理】函式與參數（命令列參數 --start、--next）

**比喻**：函式像一台「果汁機」，參數是你丟進去的水果。同一台果汁機，丟蘋果出蘋果汁、丟芒果出芒果汁——程式不用改，換參數就好。**命令列參數**則是「在終端機下指令時順便交代的話」，例如 `python load_to_supabase.py --next 2` 的意思是：「執行這支程式，順便告訴它：再加入 2 支球隊。」

專案裡真的在用的幾行（load_to_supabase.py 的 `main()`）：

```python
def main():
    parser = argparse.ArgumentParser(description="把 NBA 數據寫進 Supabase")
    parser.add_argument("--start", default=DEFAULT_START, help="開始日期，格式 2006-10-01")
    parser.add_argument("--next", type=int, metavar="N", help="再加入 N 支還沒載入的球隊")
    parser.add_argument("--progress", action="store_true", help="顯示 30 隊的載入進度")
    args = parser.parse_args()

    if args.progress:
        show_progress()
        return
    if args.next:
        ok = load_next(client, args.next)
```
- `def main():`：定義一個叫 main 的函式（果汁機），還沒開始打，只是把機器組好。
- `argparse.ArgumentParser(...)`：一個「聽指令的櫃台」，負責讀你在終端機打的那串字。
- `add_argument("--start", default=...)`：登記一種指令。沒交代 `--start` 時，就用預設值（2006 年）。
- `type=int`：把 `--next 2` 的 "2"（文字）轉成數字 2，才能拿來算。
- `action="store_true"`：開關型參數，有寫 `--progress` 就是 True，沒寫就是 False，後面不用接值。
- `args = parser.parse_args()`：櫃台開始讀指令，結果放進 `args`，之後用 `args.next`、`args.start` 拿。
- `if args.progress: ... return`：只要看進度，就印完直接結束，不抓資料。
- `load_next(client, args.next)`：呼叫另一個函式，把「要加幾隊」當參數傳進去。

每日自動更新（daily_update.py）就是幫你打這些指令：
```python
ok1 = run(["load_to_supabase.py", "--start", start] + dry, log)
ok3 = run(["load_to_supabase.py", "--next", str(TEAMS_PER_DAY)] + dry, log)
```
- `run(...)` 也是函式，第一個參數是「要打的指令（串列）」，第二個是記錄檔。
- `str(TEAMS_PER_DAY)`：指令列只能放文字，所以把數字 2 轉回文字 "2"。
- `+ dry`：如果你執行 `python daily_update.py --dry-run`，就把 `--dry-run` 也一路傳下去，全部只試跑不寫入。

## 2026-10-29｜戰術使用：冠軍靠什麼戰術得分？

### 【昨天到今天做了什麼】

昨天（10/28）網站多了「投籃分布」分頁：半場球場圖、五大區出手佔比、逐季趨勢，你也自己加上了球員篩選和多季對照。你在 Supabase 建了 `shot_zone_team` 檢視表，讓資料庫先幫忙把幾十萬次出手「分區加總」，網頁只讀幾百列；也刪掉了用不到的 Dockerfile，並用「Add files via upload」把 app.py 和兩份文件直接傳上 GitHub。今天往指定清單的第 2 項前進：新增「戰術使用」分頁，用 playtypes_team 看冠軍隊用哪些戰術、打得有多好。

### 【今天新增的比較】

- **問題**：冠軍隊的進攻，是「某種戰術用得特別多」，還是「同樣的戰術打得特別有效率」？
- **假設**：冠軍的戰術比例和聯盟差不多，真正拉開差距的是每回合得分（PPP，points per possession）。
- **圖表**：
  1. **戰術地圖**（散點圖）：橫軸＝使用率比聯盟多幾個百分點，縱軸＝每回合比聯盟多得幾分，圈越大＝回合越多。右上「多用又有效」、左上「用得少但有效」。
  2. **戰術表**：使用率（附細長條）、聯盟使用率、每回合得分、聯盟效率、效率差、聯盟排名。
  3. **八位冠軍的共同點**（熱力圖）：每一欄是一位冠軍、每一列是一種戰術，格子是聯盟排名（1＝最好）。可切換「效率」或「使用率」排名。
  4. **逐季變化**：選一種戰術，看這隊的使用率與每回合得分 vs 聯盟平均，紫色直條是奪冠球季。
  - 「看哪一端」可切換進攻／防守。防守端的每回合「失分」越低越好，所以效率差已經反過來算：正數＝比聯盟守得好。
- **讀法**：先看戰術地圖，圈是往「上」跑（效率）還是往「右」跑（使用多）？再到熱力圖切換兩種排名：如果「效率排名」一片亮、「使用率排名」亮暗混雜，就支持今天的假設——冠軍贏在把戰術打好，而不是打法特別不一樣。

### 【追加】各隊戰術比較與奪冠方程式（使用者要求）

- **問題**：把 30 隊放在一起比，哪些戰術「打得好」和贏球最有關？把這些戰術組合成一個「方程式」，冠軍會不會排在最前面？
- **假設**：和勝率最有關的是戰術的效率，不是使用率；冠軍的方程式分數會在當季前幾名。
- **圖表**：
  1. 各隊戰術比較熱力圖：一列一隊，依勝率排序，冠軍那列框起來，最下面是聯盟平均；可切換使用率／每回合得分／效率排名、全聯盟 30 隊／八支冠軍隊。
  2. 奪冠方程式長條圖：每種戰術的「效率」和「使用率」各自和勝率的相關係數（紫色＝效率、灰色＝使用率）。
  3. 檢驗方程式表格：用效率相關係數當權重，替每隊打「方程式分數」，看八位冠軍在當季排第幾，和勝率排名對照。
  4. 單一戰術散點圖：每個點是一隊一季，橫軸每回合得分、縱軸勝率，冠軍是彩色星星。
- **讀法**：先看長條圖，紫色長條明顯比灰色長的戰術，就是「打得好比用得多更重要」；再看表格，冠軍方程式排名越前面，代表方程式抓得到冠軍的特徵；排名很後面的冠軍，就是值得單獨研究的例外。

**關鍵程式**：

```python
M["eff"] = M["ppp"].where(M["side"] == "offensive", -M["ppp"])
r_eff = g["eff"].corr(g["win_pct"])
M["z"] = M.groupby(["season", "side", "play_type"])["eff"].transform(lambda s: (s - s.mean()) / (s.std() or 1))
sc["score"] = sc["wz"] / sc["w"]
```
- `.where(...)`：進攻端保留原本的每回合得分，防守端改成負的失分，讓「數字越大越好」兩邊一致。
- `.corr(...)`：相關係數，−1～+1。0.1 算弱、0.3 算中、0.5 以上算強。
- `transform(lambda s: (s - s.mean()) / s.std())`：標準分數（z 分數），意思是「比同一季聯盟平均好幾個標準差」，這樣不同年代、不同戰術才能放在一起加。
- `score = wz / w`：加權平均，越重要（相關越高）的戰術佔越多比重。
- 注意：權重和分數用同一批資料算，所以這是「描述」；真正的驗證要用前幾季算權重、拿後幾季的冠軍來測。

**關鍵程式**：

```python
def team_queue():
    done = set(CHAMPION_TEAMS) | set(read_added())
    old_champs = [a for a in dict.fromkeys(CHAMPIONS.values()) if a in all_abbr]
    order = old_champs + [a for a in all_abbr if a not in old_champs]
    return [a for a in order if a not in done]
```
- `set(...) | set(...)`：兩個集合「合併」，得到「已經有的球隊」。
- `dict.fromkeys(...)`：把重複的冠軍隊伍去掉、又保留原本順序（GSW 拿過好幾次冠軍，只留一次）。
- 最後一行是串列推導式：照順序排好，再把已經有的拿掉，剩下的就是「排隊等著載入」的球隊。
- 這支程式只有在「抓到的例行賽球季數夠完整」時才把球隊寫進 added_teams.txt；網路不穩只抓到一半，明天會自動重試，已經抓過的球季有存檔，不會重抓。

### 【今天的技術原理】變數、串列、字典

**比喻**：
- **變數**像貼了名字的盒子：`pl_team = "GSW"`，之後說 `pl_team` 就是在說 "GSW"。
- **串列（list）** 像一排有順序的置物櫃，用位置（0、1、2…）拿東西：`ALL_TEAMS[0]` 是第一個。
- **字典（dict）** 像通訊錄：用「名字」查「電話」，不用管順序：`TEAM_ZH["GSW"]` 查到 "勇士"。
- **集合（set）** 像點名單：只在乎「有沒有在名單上」，查得非常快。

專案裡真的在用的幾行，逐行拆開：

```python
TEAM_ZH = {"GSW": "勇士", "DEN": "金塊", "BOS": "塞爾提克", "OKC": "雷霆", "NYK": "尼克",
           "MIL": "公鹿", "LAL": "湖人", "TOR": "暴龍"}
```
- 一個字典：左邊是「鍵」（球隊代號），右邊是「值」（中文名）。整個網站顯示中文隊名，全靠查這本通訊錄。

```python
ALL_TEAMS = [t for t in TEAM_ZH if t in set(team_raw["abbreviation"])]
```
- 這是「串列推導式」，白話是：把 TEAM_ZH 裡每一個鍵 `t` 拿出來，**如果**資料庫裡真的有這隊，就放進新串列。
- 結果是 `["GSW", "DEN", "BOS", ...]`，順序跟 TEAM_ZH 一樣，所以網頁按鈕的順序是你決定的。

```python
CHAMP_SET = set(zip(champs["season"], champs["abbreviation"]))   # {(球季, 球隊)}
```
- `zip` 把兩欄像拉鍊一樣一對一扣起來：`("2021-22", "GSW")`、`("2022-23", "DEN")`…
- 放進 `set` 後，`("2021-22", "GSW") in CHAMP_SET` 就能瞬間回答「這是不是奪冠球季」。網站上所有 ★ 都是這樣判斷的。

### 【今天新功能的程式拆解】

```python
def prep_playtypes(pt):
    pt = pt.copy()
    for c in ["gp", "poss", "poss_pct", "ppp", "pts"]:
        pt[c] = pd.to_numeric(pt[c], errors="coerce")
    if pt["poss_pct"].max() > 1.5:
        pt["poss_pct"] = pt["poss_pct"] / 100
    pt["side"] = pt["type_grouping"].str.lower()
    keys = ["season", "season_type", "side", "play_type"]
    off = pt["side"] == "offensive"
    pt.loc[off, "rk_ppp"] = pt[off].groupby(keys)["ppp"].rank(ascending=False, method="min")
    pt.loc[~off, "rk_ppp"] = pt[~off].groupby(keys)["ppp"].rank(ascending=True, method="min")
    pt["rk_use"] = pt.groupby(keys)["poss_pct"].rank(ascending=False, method="min")
```
- `pt.copy()`：先複製一份再改，不會動到快取裡的原始資料。
- `pd.to_numeric(..., errors="coerce")`：資料庫傳回來的 numeric 有時是文字，轉成數字；轉不了就變空值，不會當機。
- `if ... > 1.5: / 100`：保險絲。使用率應該是 0～1（例如 0.12＝12%）；萬一存成 12，就自動除以 100。
- `keys = [...]`：「同一季、同一種比賽、同一端、同一種戰術」的 30 支球隊放在一組比較。
- `off = pt["side"] == "offensive"`：一整欄的 True/False，標出哪些列是進攻端。
- `rank(ascending=False)`：進攻端每回合得分越**高**排越前面（第 1 名）。
- `rank(ascending=True)`：防守端是對手的每回合得分，越**低**越好，所以反過來排。
- `pt.loc[~off, ...]`：`~` 是「相反」，也就是防守端那些列。
- `rk_use`：使用率排名，用得越多排越前面。熱力圖的兩種排名就是這兩欄。

```python
g = (pt.groupby(["season", "season_type", "side", "play_type"])
     .agg(lg_share=("poss_pct", "mean"), lg_pts=("pts", "sum"), lg_poss=("poss", "sum"), ...))
g["lg_ppp"] = (g["lg_pts"] / g["lg_poss"].where(g["lg_poss"] > 0)).fillna(g["lg_ppp_mean"])
```
- 聯盟平均使用率：30 隊的使用率直接平均。
- 聯盟平均每回合得分：**不是**把 30 個 PPP 平均，而是「全聯盟總得分 ÷ 全聯盟總回合」。某隊只打了 50 回合單打，不該跟打了 600 回合的隊伍一樣重。
- `.where(... > 0)`：回合是 0 的時候不要除（避免除以 0）；算不出來再用簡單平均補上。

```python
cur["d_ppp"] = (cur["ppp"] - cur["lg_ppp"]) * (1 if is_off else -1)
```
- 效率差統一成「正數＝比聯盟好」。防守端乘上 −1，這樣圖上「往上」永遠代表好事，讀圖時不用切換腦袋。

### 【今天新功能的程式拆解】

**1. 一頁一頁讀投籃紀錄（`load_shots`）**

```python
@st.cache_data(ttl=3600, show_spinner="讀取投籃紀錄中…（一季約 7,000 次出手）")
def load_shots(team_id, season, season_type):
    client = get_client()
    rows, start, page = [], 0, 1000
    try:
        while True:
            part = (client.table("shots")
                    .select("game_id,game_event_id,player_name,loc_x,loc_y,made,zone_basic,zone_area,shot_distance")
                    .eq("team_id", team_id).eq("season", season).eq("season_type", season_type)
                    .order("game_id").order("game_event_id")
                    .range(start, start + page - 1).execute().data)
            rows += part
            if len(part) < page:
                break
            start += page
    except Exception:
        return pd.DataFrame()
    return pd.DataFrame(rows)
```

- `@st.cache_data(ttl=3600, ...)`：讀過一次的結果記住 1 小時，同一隊同一季第二次看就不用再等。
- `rows, start, page = [], 0, 1000`：準備一個空串列裝資料；從第 0 筆開始；每次讀 1000 筆（Supabase 一次最多給 1000 筆）。
- `.select("game_id,...")`：只拿需要的欄位，不用 `*`，傳輸量少很多。
- `.eq("team_id", ...).eq("season", ...)`：**最重要的一行**。shots 有幾十萬筆，一定要先叫資料庫只給「這隊、這季、這種比賽」，不然會讀到天荒地老。
- `.order(...)`：分頁時一定要固定排序，不然第 2 頁可能和第 1 頁重複或漏掉。
- `.range(start, start + page - 1)`：第一次拿第 0～999 筆，第二次 1000～1999 筆……
- `if len(part) < page: break`：這一頁不滿 1000 筆，代表讀完了，跳出迴圈。
- `except Exception: return pd.DataFrame()`：資料表不存在或連線出錯時，回傳空表格，畫面就會顯示「尚未載入資料」而不是一片紅色錯誤。

**2. 把出手整理成「每區一列」（`zone_table` 的核心）**

```python
g = d.groupby(["zone_basic", "zone_area"], as_index=False)[["fga", "fgm"]].sum()
g["fg_pct"] = g["fgm"] / g["fga"].replace(0, pd.NA)
g["share"] = g["fga"] / g["fga"].sum()
g["value"] = g["zone_basic"].map(lambda z: 3 if "3" in z else 2)
g["pps"] = g["fg_pct"] * g["value"]
```

- `groupby([...]).sum()`：把「同一區」的出手加起來，例如「中距離（左翼）」出手 512、命中 205。
- `fg_pct`：命中率 = 命中 ÷ 出手；`.replace(0, pd.NA)` 避免除以 0。
- `share`：這區佔全部出手的比例，就是「每 100 次出手有幾次在這裡」。
- `value`：區域名稱裡有「3」（Corner 3、Above the Break 3）就是三分區，投進值 3 分，其他值 2 分。
- `pps`：每次出手平均得分 = 命中率 × 分值。**這一欄就是今天假設的關鍵**：中距離 45% × 2 = 0.90 分，三分 36% × 3 = 1.08 分。
